00一页结论

设计自洽 ✅  /  音乐化智能 ⚠️ 约 45%

流程结构有效——创作链路（灵感→歌词→风格→生成→迭代）与真实词曲创作语义、Suno 官方双模式同构；数据模型（版本树/2 变体 A/B/LRC）天然服务「二创冲动」北极星；可靠性层（串行化/心跳/限流/持久化）已通过代码评审与回归实测。

「为音乐设计而生」尚未兑现——Agent 不会评估生成结果、不会自修复失败、没有项目上下文（三个分水岭节点见 2.3）；对 MusicMake 的工具面完成度约 40%，Agent 智能面是最大缺口。这些是 P2 的核心工作，也是与标杆的差异化所在。

判断依据：第一部分为「设计自洽」提供证据；第二部分为「智能缺口」提供对标证据；验证标准为 key 到位后的实测清单。

1.4 任务状态机与数据同步规则

songs.statusdraft → processing → done / failed
↕ 轮询同步
generation_jobs.statuspending → processing → success / failed
场景规则（已实现并回归验证）
任务成功落库 2 变体 + LRC + status=done；守卫更新（并发轮询只完成一次）
成功但结果为空标记 failed（error: 生成完成但未返回音频），避免僵尸 processing
限流 429 / 服务端 5xx / 网络抖动保持 processing，进度只增不减——终态只认 Provider 状态枚举
敏感词拦截failed + 明确错误信息（内容审核未通过）
mock 服务重启任务落盘恢复 → 进行中标记中断失败 → 曲库页惰性清扫

02第二部分 · 差距审计（对标 MusicMake / 海绵音乐）

结论先行：工具面完成度约 40%，Agent 智能面是最大缺口——后者正是「为音乐设计而生」的分水岭。

2.2 Agent 智能面对标（MusicMake 的核心卖点）

MusicMake Agent 能力我们现状差距说明
「说结果，Agent 自动选工具」❌用户必须自己知道用 extend/cover 哪个工具；LLM 有工具集但无「意图→工具选择」的显式路由设计
@My Music 上下文（引用已存歌曲/上传音频/当前结果）❌对话中无法引用曲库歌曲；工具靠 songId 传参，LLM 不感知曲库
自动修复失败（版权→改写原创 / 审核→安全措辞 / 参数→补齐重试）❌失败只是如实报告，无自修复循环；sunoapi 的 SENSITIVE_WORD_ERROR 可触发改写重试，未实现
生成后评估（Agent 对比变体、判断质量）❌Agent 不「听」结果，不评估；变体对比全交给用户
创作上下文保持（不提工具、不重写提示词）⚠️ 部分pi 会话保持对话上下文；但无项目级状态（无「当前正在做的歌」概念）

2.3 海绵音乐玩法对标（国内玩法层，P2 候选）

海绵音乐玩法我们现状差距说明
一句话生成 / 对话写歌✅核心路径一致
仿写热门歌曲❌版权高风险，需法务评审前置（字节有曲库授权，我们没有）
相册成曲❌多模态输入（图片→歌曲主题），P2 后段候选
音色克隆⚠️ 未接sunoapi 有完整 Voice API（验证→录音→voiceId→persona）；声音权益合规前置
AI 改词⚠️ LLM 能力有未工具化；可做成独立工具（改词不重新生成）
参考音乐❌同 2.1 参考音频

2.4 「为音乐设计而生」的三个分水岭节点

判定标准：通用聊天 + 生成 API = 薄客户端；具备以下三节点 = 音乐域 Agent。当前完成度 ≈ 45%。

分水岭节点现状差距优先级
① 音乐结构语义 文本层结构标记（LLM 写，无程序校验） 段落级操作（按 Verse/Chorus 定位替换而非盲选时间区间）；词级时间戳对齐（sunoapi 有 aligned-lyrics API 未接）；结构校验门禁 P2
② 生成后评估与自修复 无（Agent 只报任务状态，不「听」结果） 变体对比评估（LLM 判断两变体差异与优劣）；失败自修复（敏感词→改写重试、参数错误→补齐重试）；质量门禁反馈 P2 第一优先（差异化所在）
③ 上下文与项目感 单会话聊天 + 版本树雏形 @曲库引用（对话中说「用上次那首」）；Reuse Prompt（从任意生成复用参数）；「当前项目/歌曲」的持续上下文 P2–P3

03验证标准（key 到位后的实测清单）

流程图只能证明设计自洽；以下指标是「流程是否真的有效」的实证判据——没有它们，任何图都是纸面设计。

指标怎么测通过线（建议）
一次生成可用率N 次生成中「试听后保留」的比例≥ 50%
中文歌词质量人工抽查：结构完整 / 发音友好 / 押韵自然 / hook 存在4/4 通过 ≥ 80%
迭代成功率extend/cover 任务完成率 + 用户对迭代结果的满意率完成率 ≥ 95%，满意率 ≥ 50%
二创转化生成第一首后 24h 内发起第二次生成/第一次迭代的比例≥ 30%（Suno 的核心验证信号）
体感时长提交到可试听（stream 级）的等待≤ 40s 见 stream，≤ 3min 完整
异常恢复断网/重启/限流场景下用户可理解、可恢复0 个「永久卡死」
这六项指标的基线数据，就是「为音乐设计而生」从口号变成事实的证据。

04P2 路线建议（按审计结论排序）

优先级工作项理由
P2-1生成后评估与自修复（敏感词→改写重试、参数→补齐重试、变体对比评估）Agent 智能面是唯一能做出差异化、且「为音乐设计而生」最短路径的一块
P2-2「说结果，Agent 选工具」路由 + @曲库引用 + Reuse Prompt对齐 MusicMake 的 Agent 核心体验，降低用户认知负担
P2-3参考音频输入 + 段落级操作（词级对齐驱动替换段落）+ Replace Section UI补齐两家标杆共有的创作入口，打通结构语义节点
P2-4玩法层（仿写热歌 / 音色克隆）——先过国内合规评审仿写=版权高风险、音色克隆=声音权益；海绵是字节法务背书，我们没有。备案/标识/ICP 同步排期
P2-5提取类工具（Stem / MIDI）+ 下载按钮sunoapi 已有 API，纯接入成本，按需插队
P1-4（真实 key 实测）与 P2-1 可并行：实测数据直接喂给「评估与自修复」的设计。
